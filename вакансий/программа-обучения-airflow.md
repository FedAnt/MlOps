## 1. Смысл продукта (0.5–1 день)

| Тема | Содержание |
| --- | --- |
| Роль оркестратора | Airflow планирует и запускает **задачи** с **зависимостями**, **повторами** и **историей**; сам по себе не заменяет хранилище и «не переносит данные магически». |
| Базовые сущности | DAG, Task, Operator, Task Instance, DAG Run, Scheduler, метаданные (PostgreSQL), Web UI. |
| Отличие от cron | Зависимости между шагами, backfill (идея), мониторинг, единая точка для data-пайплайнов. |

**Критерий:** одной фразой объясняете, чем DAG отличается от одного длинного shell-скрипта по расписанию.

---

## 2. Как это работает (1–2 дня)

| Тема | Содержание |
| --- | --- |
| Парсинг DAG | Scheduler периодически читает файлы из каталога DAG, строит граф. |
| Планирование | Расписание / триггеры → решение о новом **DAG Run**. |
| Очередь и зависимости | Task Instance ждёт успешного upstream. |
| Исполнение | В лаборатории — **LocalExecutor** (упрощённая модель относительно Celery/Kubernetes Executor). |
| UI | Отображение состояния и логов из метаданных. |

**Критерий:** схема «файл DAG → scheduler → БД → исполнение → UI» без шпаргалки.

---

## 3. Пользователь DAG-разработчика (2–4 дня)

| Тема | Содержание |
| --- | --- |
| DAG как код | `DAG()`, `task_id`, связи `>>` / `set_upstream`. |
| Операторы | `BashOperator`, `PythonOperator`, `EmptyOperator`; концепт Sensor / deferrable. |
| Время и идемпотентность | `logical_date`, data interval; задачи должны быть безопасны при повторном запуске. |
| Connections / Variables | Учётки MinIO/S3, URL сервисов; секреты не в коде DAG. |
| XCom | Обмен небольшими метаданными между задачами; не таскать большие данные через XCom. |
| Отладка | `airflow dags list`, Import Errors в UI, логи задачи в UI. |
| Пауза и фильтры UI | `unpause`, URL без лишних query-параметров (см. baseline). |

**Критерий:** изменили DAG в репозитории, доставили в кластер по runbook, видите результат в UI.

---

## 4. Администратор платформы (3–5 дней, частично параллельно с п. 3)

| Тема | Содержание |
| --- | --- |
| Развёртывание | Helm release, values, namespace, Ingress (Traefik), `AIRFLOW__WEBSERVER__BASE_URL` **без** завершающего `/`. |
| Компоненты | webserver, scheduler, triggerer (если включён), PostgreSQL, том DAG / при переходе — git-sync. |
| Секреты | `FERNET_KEY`, `WEBSERVER_SECRET_KEY` для стабильности сессий и предсказуемости. |
| Ресурсы и сбои | requests/limits, OOM, `kubectl describe pod`, Events, логи webserver. |
| Операции | миграции БД, пользователи UI, backup метаданных (концепт RTO/RPO для лаборатории). |

**Критерий:** после `helm upgrade --wait` знаете, куда смотреть при зависании (поды, логи, события).

---

## 5. Данные и MinIO (1–2 дня)

| Тема | Содержание |
| --- | --- |
| Connection | S3-совместимый endpoint MinIO в кластере, connection в Airflow. |
| Паттерн | проверка зоны `raw` → шаг обработки → запись в `staging` (в лаборатории — упрощённо). |
| Граница ответственности | Airflow **оркестрирует**; тяжёлая SQL/витрины часто остаются за dbt / движками — вы позже свяжете это в разделе 6. |

**Критерий:** одна задача в DAG проверяет наличие объекта в bucket или читает метаданные без «тяжёлого» ETL.

---

## 6. Сквозной мини-проект (2–3 дня) — **точка возврата после других продуктов**

Здесь закрепляется связка **оркестратор ↔ остальной стек Фазы 4**. Если сначала уходите на изучение **dbt / ClickHouse / Trino**, после них **возобновляйте с этого раздела** (с п. **6.1** чеклиста ниже).

| Тема | Содержание |
| --- | --- |
| Расписание | DAG с `schedule` или понятным триггером для лаборатории. |
| Документация | `doc_md` у DAG/задач. |
| Интеграция | вызов dbt (`dbt run` / job), запрос к Trino, загрузка в ClickHouse — по мере появления этих компонентов в кластере. |
| Надёзность | ретраи на внешних шагах, осмысленные `retries`/`retry_delay`. |
| Runbook | для себя: «webserver не отвечает», «scheduler не видит DAG», «падение задачи с MinIO». |

**Критерий:** один DAG описывает кусок пути данных через уже развёрнутые сервисы; есть короткий runbook.

## Возврат после изучения других продуктов из списка Фазы 4

**Список продуктов Фазы 4** (помимо уже поднятого MinIO и Airflow): **dbt**, **ClickHouse**, **Trino** — маршрут обучения: [`программа-обучения-dbt-clickhouse-trino.md`](./программа-обучения-dbt-clickhouse-trino.md); практика в [`план-практики-инфраструктура-senior-devops.md`](./план-практики-инфраструктура-senior-devops.md), раздел «Фаза 4».

**На какой шаг вернуться:** к **разделу 6** этой программы и чеклисту — с пункта **6.1** («Сквозной мини-проект»). Если раздел 6 **ещё не начинали** до ухода на dbt/CH/Trino — всё равно **вход в Airflow после них** с пункта **6.1**; разделы 1–5 при необходимости используйте как справочник, не как обязательный повтор с нуля.

**Связь с общим планом:** это соответствует завершению практики Фазы 4 по пункту «несколько DAG с зависимостями» и **интеграции с GitLab CI** для артефактов DAG/моделей — после того, как остальные движки в стеке уже знакомы.
